# SMA

SMA (Small Model Arena launcher) is a standalone CLI. It takes one Hugging Face checkpoint that is already in the quant you name, serves it, and writes a resumable run folder.

SMA does not quantize or convert weights. It does not use tensor parallelism, including across machines. One GPU runs one model at a time: a Spark runs one model, and the V100 pod one per GPU (`sma worker --slots`). The host alias in the run record is not a hostname, and the HF token is read from the environment or the git-ignored `.env`, never from `sma.yaml`.

SMA serves each model the way people really run it on a Spark ([docs/serving-design.md](docs/serving-design.md)). The checkpoint format picks the engine before launch:

| Checkpoint | Engine | KV cache |
| --- | --- | --- |
| Safetensors: BF16, NVFP4, mixed, MXFP4 | vLLM (default) | FP8 |
| Safetensors the pinned vLLM image cannot serve | SGLang (`--engine sglang`, `engine.name`, or chosen by preflight) | FP8 |
| GGUF (`--gguf QUANT`, for example `UD-Q4_K_XL`) | llama.cpp | Q8_0 |

The engine is part of the subject. A failed start is never retried on another engine. The KV cache is always 8-bit, never 16-bit. Context per stream starts at 64K (owner decision 2026-10-31; 256K before), or the model's native maximum if smaller, and steps down until it fits a 100 GB memory budget; see [Memory on a Spark](#memory-on-a-spark).

```bash
sma run Qwen/Qwen3-8B --bf16
sma run nvidia/Qwen3-8B-NVFP4 --nvfp4
sma run unsloth/Qwen3-8B-GGUF --gguf BF16
sma run unsloth/Qwen3-8B-GGUF --gguf UD-Q4_K_XL --reference <bf16-gguf-run-id>
sma run unsloth/Qwen3-8B-GGUF --gguf UD-Q4_K_XL --reference <bf16-gguf-run-id> --thinking on
```

Each run has a thinking mode, part of its identity (owner decision 2026-10-29). `--thinking off`, the default, turns the chat template's thinking off for every benchmark and scores quality greedily. `--thinking on` turns it on for every benchmark and sends no temperature, so the engine applies the model's own sampling (its `generation_config.json`, or a GGUF's `general.sampling` metadata on llama.cpp). Each 4-bit quant runs in both modes; BF16 runs with thinking off, as the reference for quantization damage. A thinking-on run lives beside the quant's thinking-off runs, in `<quant>-thinking`. Answers have no length limit in either mode: an answer may use all the context its stream has left, which the memory plan sets.

A pair is a reference and a 4-bit quant, run as three legs on one Spark with one engine: the reference with thinking off, then the quant with thinking off, then the quant with thinking on. Both quant legs compare their logprobs (KL) with the reference leg. A safetensors pair is `--bf16`/`--mxfp4` with `--nvfp4`/`--mixed`; a GGUF pair is `--gguf REPO REFERENCE QUANT`, two files of one repo. A leg whose run had some steps fail does not stop the legs after it; its record says what failed. `run-pair` holds one GPU lock across all legs. A queue pair is one job, pinned to the alias that created the first run, so a different Spark cannot pick up a later leg.

```bash
sma run-pair --bf16 Qwen/Qwen3-8B --nvfp4 RedHatAI/Qwen3-8B-NVFP4
sma queue add-pair --bf16 Qwen/Qwen3-8B --nvfp4 RedHatAI/Qwen3-8B-NVFP4
sma queue add-pair --gguf LiquidAI/LFM3-1.7B-GGUF BF16 QAD-Q4_0
sma worker
```

`--mxfp4` is for checkpoints that already ship as MXFP4, such as gpt-oss. A native MXFP4 model is its own reference. There is no second quant and no KL unless you compare two runs yourself.

`--mixed` is only for a checkpoint whose counted per-layer or per-group formats include both FP8 and NVFP4. The name `dgpp_mixed` is not enough. `HawkBearPig/flint-FP8-BF16` (dgpp_mixed, recipe fp8) and a dgpp_mixed config with no layer map are not `mixed`, and `--mixed` refuses them. A real FP8+NVFP4 map is still refused on stock vLLM and on stock SGLang: vLLM does not implement `dgpp_mixed`, and SGLang refuses that method too. vLLM does accept compressed-tensors configs that count both FP8 and NVFP4. SGLang refuses every compressed-tensors checkpoint. `--nvfp4` refuses mixed configs and tells you to pass `--mixed`. SMA does not flatten a mixed checkpoint into NVFP4.

## How it works

One `sma run` takes one checkpoint through these stages. Each is recorded, and a crash resumes at the stage that did not finish.

1. **Pick the engine, before the run exists.** The format decides: safetensors go to vLLM, GGUF (`--gguf QUANT`) to llama.cpp. `--engine sglang` picks SGLang for safetensors. With no flag, preflight asks the pinned vLLM image's registry whether it can load the architecture; when it cannot and SGLang's image can, SGLang serves the run. `engine.selected_by` says which (`format`, `flag`, `default`, or `preflight`) and `engine.selection_reason` why. The engine is part of the run's path, so it is settled before the folder is made. A server that later fails to start is not retried on another engine.
2. **Plan memory, before the weight download.** From `config.json` and the repo's file sizes (or the GGUF header, read through ranged requests), SMA works out the bytes of KV each token adds, then the context per stream: 64K (`memory.start_context`), or the model's native maximum if smaller, halved until one stream fits next to the weights and the engine's overhead in the 100 GB budget. What is left becomes the KV pool. Each benchmark gets the largest context that fits the streams it runs at once. A model that cannot fit is refused here, with the numbers. The plan is `manifest.json` `memory_plan`; `sma run ... --dry-run` prints it.
3. **Download and describe the checkpoint.** A pinned commit, only the files the engine loads, hashed. The quant must match the flag; for GGUF, the file's own metadata names it. Parameters are counted from the tensor shapes.
4. **Serve.** The pinned image starts with the plan's context and pool and an 8-bit KV cache: `--kv-cache-dtype fp8` on vLLM and SGLang, `-ctk q8_0 -ctv q8_0` on llama.cpp. SMA then reads the engine's own startup log for the KV type it chose and the pool it allocated, and stops the run if that log reports a 16-bit cache.
5. **Measure.** Determinism (the same prompts at batch 1, 8, and 64), logprobs on a pinned corpus (perplexity, and KL against a reference run), quality suites through the chat API (MuSiQue and LiveCodeBench among them), then KernelBench Level 1 and BrowseComp-Plus deep research with the model's own sampling in the run's thinking mode (their kernels and document search run on lab machines, and a lab judge grades BrowseComp-Plus), then speed on a restarted server, while a 1 Hz sampler records GPU clocks, temperature, power, throttle flags, and available memory.
6. **Record.** `summary.json` holds the headline numbers and the deployment notes: what someone gets running this model this way on a Spark. For example, from a run of Qwen3-0.6B on vLLM on a Spark: "bf16 weights with an FP8 KV cache on vllm: 1.5 GB of weights, 40,960 tokens per stream, 36 full-length streams by the engine's own KV report within 100.0 GB. Peak memory 95.24 GB." Containers are removed on every exit.

How each engine covers each stage:

| | vLLM | SGLang | llama.cpp |
| --- | --- | --- | --- |
| Checkpoint | safetensors (BF16, NVFP4, MXFP4, mixed) | safetensors (BF16, ModelOpt NVFP4) | GGUF files, as published |
| KV cache | FP8, `--kv-cache-memory-bytes`, `--max-model-len` | FP8, `--max-total-tokens`, `--context-length` | Q8_0, one unified pool (`-c`) shared by `-np` slots, each capped at the context |
| Quality server | batch invariant for BF16 (quantized checkpoints run their real kernels), prefix caching off | deterministic inference, radix cache off, DeepGEMM off | no batch-invariant mode; prompt cache on |
| Tool calls | `--tool-parser NAME` | `--tool-parser NAME` | the model's chat template (`--jinja`) |
| Logprobs and KL | `/v1/completions` prompt logprobs, top-64; `sma compare` | `/generate` input top-k; `sma compare` | `llama-perplexity` on the same corpus, full-vocabulary KL against a full-precision GGUF run (`--reference`) |
| Speed | `vllm bench serve` in the server container | `sglang.bench_serving` in the server container | `vllm bench serve` from the vLLM image, in its own container |

## What does not start

These commands fail in preflight, before the weight snapshot is downloaded. A dry-run only prints the plan. It does not mean the engine can load the architecture.

`RecursiveSI/flint` is `FlintForCausalLM` (`model_type: flint`). The repo has no `auto_map`. It ships `sglang/flint_sglang-0.1.4-py3-none-any.whl` and no vLLM modeling code. SMA does not install that wheel.

```bash
sma run RecursiveSI/flint --bf16
# vLLM preflight fails. The error suggests --engine sglang.

sma run RecursiveSI/flint --bf16 --engine sglang
# Stock SGLang preflight also fails. FlintForCausalLM is not in the pinned image's registry.
```

`HawkBearPig/flint-FP8-NVFP4` is the same architecture with `quant_method: dgpp_mixed` (FP8 and NVFP4 expert projections, BF16 activations).

```bash
sma run HawkBearPig/flint-FP8-NVFP4 --nvfp4
# Refused. The error says to pass --mixed.

sma run HawkBearPig/flint-FP8-NVFP4 --mixed
# Refused on vLLM. Stock vLLM does not implement dgpp_mixed.

sma run HawkBearPig/flint-FP8-NVFP4 --mixed --engine sglang
# Refused. Stock SGLang does not implement dgpp_mixed. Flint is refused either way.
```

Preflight pulls the engine image, with its own timeout and progress, then queries that image's recorded digest rather than the moving tag. If the pull or the registry query fails, SMA warns and continues when the architecture is only absent from the built-in list. Flint is still refused. A registry query that succeeds and does not list the architecture fails the run. `trust_remote_code` plus a causal-LM `auto_map` is a bypass for other architectures, and it is off by default. SMA does not install a Flint wheel.

## Quickstart

Python 3.11 or newer; the quality extra needs 3.12. [uv](https://docs.astral.sh/uv/) is the intended installer.

```bash
uv sync --extra quality
# quality is NVIDIA NeMo Evaluator (nel). The launcher itself installs without it.
cp .env.example .env            # then fill it in: HF_TOKEN, SMA_HF_CACHE_DIR, and the lab machines
```

`sma` reads `.env` from the folder it runs in each time it starts, so nothing has to be exported. A variable already set in the shell wins, and `SMA_ENV_FILE` names another file. `.env` holds what belongs to this machine and never changes: the Hugging Face token, the weight cache (`SMA_HF_CACHE_DIR`, which overrides `hf.cache_dir`), the names of the KernelBench service and the x86_64 runner (SWE-bench and BrowseComp-Plus's search), and the judge's key (`OPENROUTER_KEY`; a lab judge's endpoint and key are `SMA_JUDGE_URL` and `SMA_JUDGE_API_KEY`). Run records name those machines `${NAME}`, never by value, and never hold a key. `.env.example` lists every variable.

Edit `sma.yaml` if you need to. The host alias defaults to `gpu-host-1`. It must not be a real hostname.

```bash
sma doctor
sma run Qwen/Qwen3-8B --bf16 --dry-run
sma run Qwen/Qwen3-8B --bf16 --tool-parser hermes   # the tool-call parser for this model
sma status
sma watch                       # live view of everything running; ? for keys, q quits
sma list
sma resume <run-id>
sma resume <run-id> --redo browsecomp_plus   # run a finished benchmark again (a quality suite, browsecomp_plus, kernelbench)
sma rescore <run-id>            # score saved quality output again with this SMA; no model runs
sma compare <bf16-run-id> <nvfp4-run-id>
sma publish-check --fix runs/<model>   # before you commit run folders: scrub again, refuse anything private
```

`sma watch` is an interactive screen on a terminal and plain text with `--once` or when piped; its panels and keys are under [The sma watch screen](#the-sma-watch-screen). It reads every 5 seconds (`--interval`). MACHINES lists each machine SMA uses, by kind and chip and never by name: this Spark (product, GPU, CPU cores, memory and what is free), the KernelBench service (its GPU, CUDA, and torch, from `/v1/environment`; it reports no machine type), the x86_64 runner (a read-only script over SSH), and the judge (whether its endpoint lists `browsecomp.judge_model`; its API reports no hardware). Each is asked at start and every minute, and shows as up, down, or not set in `.env`. QUEUE lists the pending and claimed jobs in the order they start, each line led by its engine and its place. CURRENT RUN has one line per benchmark, in the order the run does them: determinism, perplexity (and KL for a quant with a reference), each quality suite, KernelBench, SWE-bench (when the run has it on), BrowseComp-Plus, and speed. Each shows its score (as a percentage, colored from red at 0 through orange and yellow to green at 100), its progress (a nel suite's answered count from `inference_log.jsonl`, whose first line records the config and is not counted; BFCL's from the eval-factory container's per-category result files, out of the suite's limit (or its dataset size); LiveCodeBench's from its eval-factory proxy's running totals (`response_stats_cache/cache.db`, read only while the container has it open), with answers cut off at the end of the context and, once all are answered, "running the tests" until its graded file (`*_eval_all.json`) is written, since its own answers file is saved only once its batch is done (`cache_batch_size`, one batch of all its problems in sma.yaml: with the container's 10, each batch waited on its slowest answer with one stream busy); KernelBench's kernels written; BrowseComp-Plus's questions answered; SWE-bench's finished tasks of 50 by how each ended, submitted or at the step limit, read from the runner over SSH at most once a minute; and for the agent steps the time since this attempt began, from its `settings.json`, with the attempt number when a step is redone), its error, or queued. Suites run one at a time, so a suite with an unfinished attempt that is not the one running shows as stopped: a stop cut it short, and a resume starts it again. Setup and bookkeeping steps (fetch, servers, results, teardown) get a line only while running or failed. SERVING shows each rate as average/peak (the average in blue, the peak in purple; the peak is the highest rate over one pair of samples, 15 s apart, in that window): prefill and decode tok/s per stream (what one request sees while sharing the server), decode tok/s over all streams (the server's total: generated tokens over wall-clock time), and inter-token latency. Prefill has no all-streams row: prompts take a sliver of the server's time, so prompt tokens over wall-clock time measure how fast prompts arrive, not a speed. The first columns are the current run only: since its server started, and its last 5 minutes, hour, and 24 hours, from its own counters (`engine_metrics.jsonl`). One more column, "24 h, all", is every run of the last 24 hours together, whatever engine served: tokens and seconds are summed across whatever served in the window, over the pairs of samples that report both, then divided (SGLang's prefill time is each request's `prefill_forward` stage of `sglang:per_stage_req_latency_seconds`, which builds after v0.5.10 report. Its prefilled and decoded tokens are the scheduler's `sglang:realtime_tokens_total`, modes `prefill_compute` (prefix-cache hits not included) and `decode`, which grow as it works. `prompt_tokens_total` and `generation_tokens_total` grow only when a request ends, so a long answer read as zero and then as one burst. SGLang v0.5.10 reports neither, so it adds nothing to prefill or to decode over all streams), after a "since start" column read live from the current server, whose counters run from its start (the all-streams rate there divides by the container's uptime from `docker inspect`). For a run that records no `engine_metrics.jsonl` (one started before SMA recorded them), `sma watch` keeps its own reads of the server, so its windows cover only the time `sma watch` has been open. Each engine's formulas live in its backend (`serving_rates`, which also derives TTFT and all-stream rates where the engine reports them). llama-server adds a request's tokens to its counters when the request ends, so with long requests a 5-minute window is uneven; the hour and the day even it out. FINISHED lists the latest 3 runs that are not running, with their scores: with `--config`, those served where the config serves (the serving machine's GPUs with `remote.enabled`, else this Spark), so the V100 view does not mix in the Spark's runs; plain `sma watch` lists every run. A run is labeled by its steps, not the catalog's status: done (every step succeeded), failed (every step ran, some failed), or stopped (steps left; `sma resume` goes on from them). The catalog calls a run failed as soon as one step is and stamps it finished whenever its process ends, so a run stopped on purpose would otherwise look lost. The current run is the one with a container up, or one that wrote to its folder in the last 10 minutes. A record still "running" with neither counts only while a process holds the GPU lock (read from `/proc/locks`; the lock is not touched), so a run left "running" by a crash or a machine that went down is shown stopped, not running. `--plan FILE` adds runs a script will start: one `REPO QUANT` per line, in order, and an optional `since TIME` line (ISO time or run id) so older runs of the same checkpoint do not count. Each line shows its newest run since then, or queued. It reads files, `docker ps`, and the services' status endpoints only, and scrubs the screen like a run record (`<host>` for this machine, `${NAME}` for lab machines, no keys), so a screenshot is safe to share.

`sma doctor` checks Docker, the configured image, `nvidia-smi`, that the GPU has no compute process, free disk, that the Hugging Face cache path does not contain the hostname, and that `HF_TOKEN` is set. It does not pull the image and it does not print the token.

Fetch refuses a snapshot path that contains the hostname, because that path goes into the run record. The default cache is under your home directory. On a machine whose user name is also its hostname, that path fails. Set `SMA_HF_CACHE_DIR` in `.env` (or `hf.cache_dir` in `sma.yaml`) to a path outside your home directory.

A dry-run prints the plan and the exact commands. It downloads no weights, starts no container, and writes no run folder. It does read the repo's `config.json` and file sizes from the Hub (for GGUF, the file's header through ranged requests) to print the memory plan: the engine and why, the KV type, the context per stream and why, the memory split, the streams that fit, and each benchmark's context. Offline, or for a repo it cannot read, it says so and prints the commands with placeholders. It also does not prove the checkpoint's architecture is registered.

## What a run does

Each step is idempotent. A `steps/<name>.done` marker is written only after the step finishes. `sma resume <run-id>` skips steps that have a marker, and only on the host alias that started the run. A crash mid-step redoes that step and does not redo finished ones. The steps a resume runs use the resuming process's config. When it differs from the recorded `config_snapshot`, the old snapshot moves to `config_history` with the time it stopped applying (`until`), so the manifest shows the settings each step ran with; each quality suite's folder also keeps the config its harness read. `--redo NAME` (repeatable) runs a finished benchmark again on a resume. A quality suite loses its marker and the quality step's, and its earlier attempts stay in its folder. `browsecomp_plus` or `kernelbench` loses its two steps' markers, and its folder moves to `redone/<name>-<n>/` (git ignores the text bundle there too), so it starts again from nothing. The manifest's `redone` keeps when, by which SMA commit, and the earlier score. Nothing else reruns.

A step that fails does not stop the run, except fetch and the quality server, which everything after them needs (owner decision 2026-10-29). The step is marked failed with its error in the manifest, the run goes on to the next step, and at the end `sma run` exits 2 naming the failed steps (`RunIncomplete`); `sma resume` retries just those. Inside quality, a suite that fails gets a `scores.json` with its error and no `.done`, and the other suites still run. So a speed bench that fails still lets KernelBench and BrowseComp-Plus be scored, and a judge outage loses only BrowseComp-Plus's score until a resume.

1. **Fetch.** Resolve the repo to a commit SHA. Read `config.json` and, when present, `hf_quant_config.json`. Refuse a quant mismatch or an unsupported quant/engine pair before the weight snapshot. Pull the engine image and query its digest for the architecture registry. Flint is refused. If the image cannot be queried, an unknown architecture is a warning and the download continues. Then download that commit with `huggingface_hub` (resumable) into a plain folder, `<hf.cache_dir>/<model>/<sha>`. The engine container mounts only that folder at `/model`, so it holds real files, not the Hugging Face cache's links. Hash the weight files. Count total and active parameters from safetensors shapes. Flags are `--bf16`, `--nvfp4`, `--mxfp4`, `--mixed`, and `--gguf QUANT`. Before the weight download, SMA plans memory from `config.json` and the file sizes and refuses a run that cannot fit (see [Memory on a Spark](#memory-on-a-spark)). For `--gguf QUANT`, SMA picks the one file, or the one complete split set, whose path holds that quant as a whole token (`Q4_K` does not match `Q4_K_M`). It reads the GGUF header through ranged requests, plans, then downloads only those files. The file's own metadata gives the quant type (`general.file_type`), the tensor types, the parameter count, the KV layout, the native context, and a tokenizer fingerprint. SMA never makes or converts a GGUF. An unmatched quant names the ones the repo has.
2. **Serve for quality.** The pinned image, then the digest recorded from `docker image inspect` on later starts. vLLM: `VLLM_BATCH_INVARIANT=1` when the architecture allows it and the checkpoint is not quantized (NVFP4, MXFP4, mixed, and FP8 run their real kernels; see Caveats), `--no-enable-flashinfer-autotune`, `--no-enable-prefix-caching`, `--no-async-scheduling`, fixed seed, `--tensor-parallel-size 1`, and `--default-chat-template-kwargs` from `quality.chat_template_kwargs` (thinking off for every quality client). With `--tool-parser NAME`, `--enable-auto-tool-choice --tool-call-parser NAME`. SGLang: `--attention-backend flashinfer`, `--tp-size 1`, `--enable-deterministic-inference`, and `--disable-radix-cache` because FlashInfer determinism does not keep the radix cache, and `--tool-call-parser NAME` with `--tool-parser`. SGLang also runs with `SGLANG_ENABLE_JIT_DEEPGEMM=0`, because DeepGEMM in the pinned image does not support the GB10 and deterministic serving crashed at CUDA-graph capture without it, and with `SGLANG_FLASHINFER_WORKSPACE_SIZE` at 2 GiB: the 384 MiB default ran out on a long prefill with LFM3-1.7B's sliding-window layers and the server died mid-BrowseComp-Plus (2026-10-31). llama.cpp: `llama-server` from the pinned image with `-ngl all`, `-fa on`, `-ctk q8_0 -ctv q8_0`, one unified KV pool (`-c`, `--kv-unified`) shared by `-np` slots, each capped at the context per stream (`--kv-unified-per-slot`), `--cache-ram` (its host prompt cache, counted in the plan), `--metrics`, `--jinja` for tool calls (no parser flag), and `--chat-template-kwargs` from `quality.chat_template_kwargs`. Every engine gets its context and KV pool from the memory plan and an 8-bit KV cache: vLLM `--kv-cache-dtype fp8 --kv-cache-memory-bytes --max-model-len`, SGLang `--kv-cache-dtype fp8_e4m3 --max-total-tokens --context-length`. After a start, SMA reads the engine's own log for the KV type and the pool it allocated (`engine.kv_cache_reported`); a 16-bit KV cache there stops the run. Health check with a deadline.
3. **Determinism.** The same prompts at batch sizes 1, 8, and 64, on the quality server with prefix caching off. A mismatch is recorded. The run continues. llama.cpp has no batch-invariant mode and caches prompts; the probe still runs there and records what it sees.
4. **Logprobs.** The pinned corpus is cut into 2048-token windows and scored as raw token ids, with no chat template. vLLM uses `/v1/completions` `prompt_logprobs`. SGLang uses `/generate` input-token top-k. Each position stores top-k (default 64), a tail bucket, and the true next-token logprob. Perplexity is `exp(-mean logprob)`. A field the server does not return stays null. llama-server returns no prompt logprobs, so a llama.cpp run stops its quality server and runs llama.cpp's own `llama-perplexity` on the same corpus text instead, with the same Q8_0 cache: `logprobs.llamacpp_chunks` chunks of `logprobs.window_tokens`, scoring the second half of each (1,023 tokens per 2,048-token chunk). A full-precision GGUF (`BF16`, `F16`, `F32`) writes its full-vocabulary logits to `logprobs/kld-base.bin`. A quant started with `--reference <that run>` reads them and writes `kl_vs_reference.json` from llama.cpp's own KL statistics (mean, median and p99 KLD, same-top-token share, RMS Δp, PPL of both). That reference must be a llama.cpp run of the same tokenizer with the same chunk count.
5. **Quality.** One suite at a time against the local server's chat API, at the concurrency in `sma.yaml`: NVIDIA NeMo Evaluator (`nel`) for most suites, and an NVIDIA eval-factory container run directly for BFCL. Per-question rows, scores with an interval, and the harness's own output are saved. Each suite's `scores.json` records the context per stream the memory plan gave quality's streams (`context_per_stream`). It also records `measures`: every measure an lm-eval task scored per question, as a share. For IFEval those are strict and loose accuracy, by prompt and by instruction. The headline is strict by prompt (`prompt_level_strict_acc`), the strictest of the four; model cards often quote a loose or by-instruction one, which can run 10 points higher. By-instruction accuracy counts every instruction across all prompts. The summary repeats `measures` for each suite. LiveCodeBench (owner decision 2026-10-29, in place of SWE-bench) is one of them: NVIDIA's eval-factory container (`livecodebench:26.03`, task `codegeneration_release_v6`) asks for one answer per contest problem among LiveCodeBench's newest 105, 15 February to 1 May 2025 (owner decision 2026-10-30; its leaderboard window from August 2024 holds 454 and took about 10 hours a run), and runs each answer's code against the problem's hidden tests; the headline is pass@1, with one row per problem (its code, its answer, pass or fail). The container sends temperature, top_p, and an answer limit itself, so SMA sets them (`sampling: true`): greedy with thinking off; with thinking on, what the engine applies to a request that sets none (llama-server's `/props`, or the checkpoint's `generation_config.json`); and `quality.max_tokens`, or the context per stream minus 4,096 for the prompt if that is less. `command.json` records the sampling and where it came from. The container downloads the dataset (4.5 GB, `livecodebench/code_generation_lite`, unpinned; last changed 2025-06-05) into `hf.cache_dir/eval-factory`, once. LiveCodeBench has no problems after April 2025, so models trained since may have seen them. SMA patches one thing in that container at run time (`src/sma/patches/livecodebench`, mounted read-only and put on `PYTHONPATH`; `command.json` records its name and hash): its runner grades each test with `--timeout`, the request timeout, and never reads `--evaluation_timeout`, LiveCodeBench's 6 seconds per test. SMA gives requests hours so long answers can finish, which gave each test hours too: an answer that never stops held grading for 4 hours, and a correct answer slower than 6 seconds passed. With the patch, grading uses `--evaluation_timeout` and requests keep `--timeout`. LFM3-1.7B's BF16 run (20261030T045832Z-157bb315) was graded before the patch. MuSiQue (owner decision 2026-10-28) is one of them: 100 seeded questions from MuSiQue-Ans v1.0 dev, each with its own 17 to 20 Wikipedia paragraphs, asked with LongBench's musique prompt word for word and scored by rule with MuSiQue's own `metrics/answer.py` (`src/sma/nel_benchmarks/musique.py`). The headline is answer F1, the best over the answer and its aliases; exact match is `scorer_shares.exact_match`. The dev file comes from the `dgslibisey/MuSiQue` mirror at a pinned revision and must match the official release's SHA-256.
6. **KernelBench.** On the quality server, the model writes a kernel for each of KernelBench's 100 Level 1 problems (shipped in `src/sma/data/kernelbench/` at commit `423217d9`, the one the service runs). The prompt is KernelBench's one-shot CUDA fp32 prompt, sent as a chat with its system prompt, `kernelbench.concurrency` at a time. Requests set no sampling field, so the engine applies the checkpoint's `generation_config.json`, and they pass `enable_thinking` as the chat template's own default (`sma/thinking.py` renders the template to find it). The kernel is KernelBench's `extract_first_code` after the reasoning block. All kernels go to the service at `KERNELBENCH_URL` as one job, and the step ends: the service compiles, checks, and times them on its own GB10 while the run goes on.
7. **SWE-bench.** Off by default since 2026-10-29 (owner decision: a run spent most of its time here, and small models mostly hit the step limit); LiveCodeBench replaces it, and `swebench.enabled: true` brings it back. When on: mini-swe-agent's own `swebench.yaml` runs the 50 Verified-mini tasks on the x86_64 runner, `swebench.workers` agents at once, `swebench.step_limit` steps each, against this run's server. SMA logs in with `SWE_RUNNER_HOST`, `SWE_RUNNER_USER`, and `SWE_RUNNER_SSH_KEY`, writes its settings next to the run's folder there (the model, the port, the step limit, the template's thinking default, and `cost_tracking: ignore_errors`, because LiteLLM has no price for a checkpoint served here and mini-swe-agent otherwise stops every task on its first call; no sampling field), forwards the server's port to the runner's loopback over SSH, and starts the agent detached, so a dropped connection does not stop it. A task that ends in anything but the model's own result (`Submitted`, `LimitsExceeded`, a format error, a full context) lost the model; SMA drops those and launches once more. Then the SWE-bench harness grades the patches there. SMA brings back the patches, the harness report, each task's exit status, the logs, and the trajectories, scrubbed. The score is resolved over 50, null if any task still has no answer. The agent acts through a bash tool call, so the run needs `--tool-parser`.
8. **BrowseComp-Plus.** Deep research over a fixed set of 100,195 web documents (owner decision 2026-10-28). On the quality server, the model answers 100 of BrowseComp-Plus's 830 questions, the same seeded 100 for every model, `browsecomp.workers` at a time. Each question runs as the repo's chat client with native tool calls (`search_agent/glm_zai_client.py` at `04694903`) runs it with its defaults: its prompt without a system message, one `search` tool returning the top 5 BM25 hits, each cut to its first 512 tokens, one 20,000-token output budget for the whole conversation, and up to 100 replies. A question ends when a reply calls no tool; it counts as answered only if that reply stopped on its own. Requests set no sampling field and pass the chat template's own `enable_thinking`, as for KernelBench. The index and its search server run on the x86_64 runner (`services/browsecomp-plus`, the `SWE_RUNNER_*` machine), so the document store takes no memory or CPU from the Spark. SMA starts the server there, reaches it through an SSH forward, and stops it after the last question. SMA departs from the client in three ways, recorded in `settings.json`: reasoning is read from vLLM's `reasoning` field as well as `reasoning_content` and kept out of the history, as the client intends; tool arguments that are not JSON go back to the model as a tool error instead of ending the whole run; and a request the server refuses, such as one past the context, ends that question as wrong. The questions and answers are read from the runner and kept only in memory and in git-ignored files. The run needs `--tool-parser`.
9. **BrowseComp-Plus results.** Right after BrowseComp-Plus, before speed (owner, 2026-10-29), the judge grades each answer that finished: model `browsecomp.judge_model`, Qwen 3.8 Flash on OpenRouter since 2026-11-04 (`qwen/qwen3.8-flash-20260826`, served by Alibaba), at `browsecomp.judge_url` with its key from `.env` under `browsecomp.judge_key_env` (`OPENROUTER_KEY`, which SMA scrubs from records), so the judge runs on separate hardware, and a judge outage fails this step only; the run goes on. Before, it was the lab's FP4 copy (2026-11-01 to 2026-11-03) and Ornith 1.5 122B, each at `SMA_JUDGE_URL` with `SMA_JUDGE_API_KEY` ([`docs/judge.md`](docs/judge.md)); an empty `judge_url` still means `SMA_JUDGE_URL`. The prompt is BrowseComp-Plus's leaderboard grader (`scripts_evaluation/evaluate_run.py`), word for word, sent one at a time with thinking off (OpenRouter's `reasoning.enabled` false), temperature 0, and 4,096 tokens, only to providers OpenRouter lists as not collecting prompts; `scores.json` records the judge, its URL when public, and these settings; its `correct: yes|no` line is read with the repo's own parser. The headline is accuracy over the 100: an unfinished question, or a judge reply without a verdict, counts as wrong, as in BrowseComp-Plus, and the run warns with the count. A request the server refuses (a 4xx, such as a full context) ends that question as wrong; a server that is down, times out, or fails (5xx) through every retry fails the step instead, and a resume asks the rest (KernelBench does the same). Before 2026-10-31 the retries hid that difference, and LFM3-1.7B's BF16 run scored 0 on 100 questions asked of a crashed server. Evidence recall (the share of each question's evidence documents its searches returned), gold recall, and search calls need no judge. Calibration error is null: the repo's formula needs at least 100 judged confidences and drops its last bin. `per_query.jsonl` keeps numbers and verdicts only; the conversations, the judge's replies, the questions, and the answers go into the git-ignored `trajectories.jsonl.gz`, whose hash the manifest keeps. Compare scores only within one judge.
10. **KernelBench results.** Before speed, SMA waits for the service's job, which has had SWE-bench and BrowseComp-Plus's time to finish (`kernelbench.wait_s`), stores its results, and scores them with KernelBench's own `score.py` formulas: correctness over 100, and fast_p, the share correct and faster than the stored eager-PyTorch time by more than p, over the problems with a stored time (99: problem 95 fails in KernelBench itself). The headline is fast_1. Compare scores only within one service fingerprint.
11. **Speed.** The server is restarted with batch invariance off. A fresh speed server, including on resume, runs the warm-up soak again. Each attempt's bench command writes `speed/cells/<cell>/attempt-<n>/bench.json`, which is the file SMA reads. Both benches run with `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1`, and both pass `--tokenizer /model` so the tokenizer is the pinned snapshot. vLLM keeps `--model` as the served name and uses `vllm bench serve` with ttft, tpot, itl, and e2el at 50, 90, and 99. SGLang passes `--model /model` as well, and uses `sglang.bench_serving` with `--dataset-name random`, a pinned local dataset at `/sma-run/speed/sglang-random-dataset.json` (so the container does not download ShareGPT), `--random-range-ratio 1.0`, `--seed`, and `--output-details`. `speed.num_prompts` above that file's row count is refused. A bench that finishes fewer prompts than `num_prompts`, or reports request errors, marks the cell `bench_failed` and retries it once after a backoff, with no cool-down. Only a thermal or power throttle is `throttled` and waits for the GPU to cool. A telemetry gap is `telemetry_gap` and is not retried. That tool's summary, in tag `v0.5.10.post1` (`python/sglang/bench_serving.py`), has median and p99 TTFT/TPOT, median/p95/p99 ITL, and median/p90/p99 end-to-end latency (`median_e2e_latency_ms`, `p90_e2e_latency_ms`). It does not emit p90 TTFT, TPOT, or ITL. SMA computes those from the per-request arrays when they are present, and otherwise stores null with a reason. The file is JSONL and is parsed from the last JSON object, so a retry cannot glue two objects into one invalid document. SGLang serve passes `--enable-metrics`, `--max-running-requests` (the same cap as vLLM `max_num_seqs`), and `--random-seed`. A failed `/metrics` scrape stores null counters and a reason. It does not fail the cell. llama.cpp's image has no bench client, so a llama.cpp run starts `vllm bench serve` from the pinned vLLM image in its own container (`<run>-bench`, host network, the host user, offline) against llama-server, with the same arguments as for vLLM and `--tokenizer /model/<file>.gguf` (the GGUF's own tokenizer). When the vLLM image's transformers cannot read the GGUF's architecture (`lfm3` on its transformers 5.6), the bench loads another tokenizer instead, downloaded at a pinned commit and mounted at `/bench-tokenizer`: the first, in this order, whose every token id and BPE merge matches the GGUF's while the GGUF's other ids are unused padding. First the source model the GGUF names (`general.base_model.0.repo_url`), then the model its repo's name says it was converted from (the name without `-GGUF`). With neither, speed is refused and the error names each one tried. LFM3-VL-2B's GGUF names LFM3-1.7B-Base, which has two audio tokens where the VL model has padding, so its speed was refused until 2026-11-02; LiquidAI/LFM3-VL-2B matches it. The bench only builds prompts of set lengths and counts tokens with it. `engine.bench_tokenizer` records which tokenizer it used and why. The manifest records that image as `engine.bench_image`.
12. **Telemetry.** A 1 Hz `nvidia-smi` sample of SM clock, temperature, power, and throttle reasons for the whole run. A real thermal or power slowdown marks that speed cell invalid and retries it once after a cool-down. `sw_power_cap` is always stored. It invalidates a cell only when `telemetry.sw_power_cap_invalidates` is true, because a GB10 near 140 W can show that flag in steady state. A cell is `unverified` unless it has about `duration / interval` samples (`telemetry.min_sample_ratio`, default 0.8) and its largest gap is no bigger than `telemetry.max_sample_gap_s`. `[N/A]` flags are unverified too. The sampler's failure counter is not used, because a later success resets it. Unverified cells are not retried. Invalid and unverified cells stay on disk and are left out of the headline tok/s.
13. **Teardown.** The container is removed on success, failure, Ctrl-C, and SIGTERM. The page cache is dropped when the process is allowed to write `/proc/sys/vm/drop_caches`. The run then waits until the GPU is cool, or until the idle timeout.

Headline tok/s uses `speed.derive_stat` (`p50` by default, or `p90` / `p99`):

- prefill tok/s = input length / TTFT at concurrency 1
- decode tok/s = 1 / TPOT at concurrency 1

If that percentile is absent, the derived number is null and the cell records why. SMA does not invent it.

`sma compare <reference> <candidate>` computes per-token KL with an epsilon floor (`1e-12`) instead of dropping positions. A probability that was actually zero is counted in `kl_infinite_positions` before the floor. `kl_floored_positions` counts every position that hit the floor, including those zeros and merely tiny positive masses. It also records top-1 agreement and delta perplexity, and it records k. It accepts a BF16 reference against a `mixed` candidate when the tokenizer, corpus, and engine match. It refuses a different engine unless you pass `--allow-cross-engine`, and that result is labeled `CROSS-ENGINE`. Different image digests are labeled `IMAGE DIGEST` and are not refused. It refuses when the tokenizer fingerprints differ, or when the token-id windows differ.

`kl_vs_reference.json` also reports the statistics of llama.cpp's `--kl-divergence`: `kl_mean_se`, `kl_quantiles` (p50, p90, p95, p99, p99.9, max), `top1_agreement_se`, `ln_ppl_ratio` with `ln_ppl_ratio_se`, and `rms_delta_p` on the true token. Standard errors are cluster-robust with one cluster per window, because positions in a window share context. The KL is coarse-grained (reference top-k ids plus one tail bucket), so it is a lower bound on full-vocabulary KL. On a GB10 with batch invariance on, two BF16 runs of Qwen3-0.6B gave identical logprobs at all 98,256 positions, so the BF16-vs-BF16 noise floor there was exactly zero.

For MoE NVFP4, MXFP4, and mixed on vLLM, SMA always passes `--moe-backend`. The chain is `flashinfer_b12x`, then `marlin` if that server never becomes healthy. Quality and speed each record the backend that started. Auto-selection is not used. Dense NVFP4 sets `VLLM_NVFP4_GEMM_BACKEND` from `engine.linear_backend` (default `flashinfer_b12x`, passed as `flashinfer-b12x`): vLLM 0.21 has no `--linear-backend` flag and refused it on a Spark. BF16 does not get the FP4 MoE backend. SGLang does not take that chain. Its MoE fields stay unset unless a log line names a backend. SMA does not invent one.

NVFP4 on vLLM includes ModelOpt W4A4 and compressed-tensors `nvfp4-pack-quantized` when the activation scheme is also 4-bit float (for example a group whose `input_activations.num_bits` is 4). A compressed-tensors group with fp4 weights and `input_activations: null` is `nvfp4_w4a16`. `--nvfp4` refuses it and will not label it `nvfp4`. SMA does not serve W4A16. SGLang NVFP4 is ModelOpt checkpoints. SGLang refuses compressed-tensors NVFP4, FP8, and mixed FP8/NVFP4, and the error says to use vLLM.

## Watching a run

The terminal shows one readable line per event: each step as it starts and finishes, retries, warnings, and server startup. `logs/sma.log` in the run folder keeps the same events as JSON, one object per line.

The engine's own output goes to `logs/server-quality.log` and `logs/server-speed.log`. SMA copies it there live while the server runs, so `tail -f` shows what the engine is doing. Lines appear as they arrive, so stdout and stderr are interleaved. Two lines written at the same instant can swap. While a server starts, the terminal prints a progress line about every 15 seconds with the newest line of that log. If the container exits before it is healthy, SMA stops waiting at once and puts the last log lines in the error.

If a server stops while a step is sending it requests, the step error says so, with the exit code and the last server log lines. A clean shutdown with no error in the log means something on the host stopped the server. On a Spark that runs earlyoom, check `journalctl -u earlyoom`: it stops `vllm` and `python` processes when free memory falls under its floor (8% on our Spark). The memory plan keeps a run's footprint under `memory.budget_gb` for that reason.

### The sma watch screen

On a terminal, `sma watch` is an interactive screen (curses, from the standard library). Piped, or with `--once`, it prints the same main screen as plain text. It only reads, and it changes nothing.

The top line says whether everything is healthy: `✓ healthy`, or how many problems (red ✗) and warnings (yellow !) there are. Then what runs (slots busy, or runs), the queue's size, KernelBench's queue, and free memory. Each problem and warning has its own line under it:

- the dispatcher is not running while a slot is busy or jobs wait (the alert says how to start it), or has not written its state for 2 minutes (3 queue polls, if longer);
- a slot is down; the memory guard stopped a run in the last hour;
- this machine has under 16 GiB free; a machine SMA uses does not answer;
- a running run's step failed; a step has run more than twice its usual time and 15 minutes over it (the median of that step's finished first attempts in this runs folder on the same hardware, once there are three); a running run's folder has had no write for 10 minutes;
- a queue claim's heartbeat is over 5 minutes old; a leg failed for good.

The top line and each alert wrap onto a second row rather than lose their end. The panels follow, what runs first, then what is next. MACHINES. The running panel: SLOTS when the config has slots (each slot idle until a dispatcher runs; a slot whose unit process is gone is idle, whatever a stopped dispatcher last wrote), CURRENT RUN for one run, or RUNNING for several runs without a dispatcher (each with a container up or a write in the last 10 minutes). Plain `sma watch` shows every run, whatever config started it: the slots of every dispatcher whose state is in the queue, this Spark's runs at work beside them (a `spark` line each), and FINISHED for every machine, each run served off this Spark marked with its hardware (`on v100`). `--config` narrows the screen to that config: a serving machine's config shows its slots and the runs served there; a Spark's config shows the Spark's runs, with one line counting the runs on a serving machine's slots. Only runs served on this Spark count as its runs: a slot's run has a container here only while a grader runs here (BFCL's). SLOTS and RUNNING have one line per slot or run: its model, its time so far, what it is on and how far, and its decode rate per stream over the last 5 minutes. Under them, the selected run shows whole, one line per benchmark as CURRENT RUN shows a run alone; ↑ ↓ pick which run, and it stays while another panel has the focus. `--once` prints every busy slot's run. QUEUE, one line per job, with each leg's state and slot. KERNELBENCH, the service's queue in the order it takes jobs. SERVING: the current run's table, or with several runs one row per run over its last 5 minutes and every run over 24 hours; one line when nothing is serving, or when the screen is too short for the table. FINISHED, newest first; the screen scrolls through all of them, and `--once` prints 3. From 190 columns there are two columns: the running panel and FINISHED on the left, the rest on the right. A panel short of rows shows what fits around its selection and counts the rest on its title line.

A run's detail has where it runs and its folder; the same one list as the main screen, with whole errors (a run no longer at work shows what its record left running as stopped); its serving windows; and the last 12 events of `logs/sma.log`. Files, the queue, and `docker ps` are read every `--interval` seconds (5), the KernelBench service every 15 seconds, and the machines and SWE-bench progress every minute. Reading runs beside the screen, so keys answer while a machine that does not answer is asked.

## Queue

Up to three Sparks can run `sma worker` against one queue directory. The directory has to be on a single filesystem because a claim is an atomic `link`. The worker takes the GPU lock before it claims. If the lock is busy it does not take a job. Each claimed job is heartbeated until it finishes. One failed model is marked failed (or returned to pending while `attempts` is under `queue.max_attempts`) and the worker continues.

A pair is one claim. The alias that created the first run is stored on the job and is not cleared when the claim is reclaimed. Leg 1 runs on that same Spark. `sma resume` refuses a run whose `host_alias` is not this process. If that Spark is gone, `sma queue unpin JOB` or `sma queue reassign JOB --host ALIAS` clears the run ids and starts the job fresh on the next host. It does not resume the old run on a different machine. A failed attempt waits (`queue.retry_backoff_s`) and then sorts behind jobs that have not failed. A pending file that is not valid JSON is logged and moved to `corrupt/`.

```bash
sma queue add Qwen/Qwen3-8B --bf16
sma queue add org/model --nvfp4 --engine sglang
sma queue add Qwen/Qwen3-8B --bf16 --tool-parser hermes
sma queue add unsloth/Qwen3-8B-GGUF --gguf UD-Q4_K_XL
sma queue add unsloth/Qwen3-8B-GGUF --gguf UD-Q4_K_XL --thinking on
sma queue list
sma queue reclaim          # return a claim whose heartbeat is stale (--older-than SECONDS after you stopped the worker)
sma queue remove <job-id>  # take a pending job that has not started off the queue (kept in removed/)
sma queue unpin <job-id>
sma queue reassign <job-id> --host gpu-host-2
sma queue drop <job-id>    # take a job off the queue even if it started (its worker must be gone, or be --config's dispatcher); its runs stay resumable
sma worker --once
sma worker --slots --config sma-v100.yaml   # one run per GPU slot of a serving machine (below)
```

`gpu.lock` stops two SMA processes on the same Spark from starting two models. `run-pair` holds that lock for every leg. `sma watch` shows each queued job on one line, with every leg's state.

`sma rescore <run-id>` scores a finished run's quality suites again from the output their harness saved, with this SMA, and asks nothing of a model. Fields SMA records now (IFEval's four measures, `answers_cut_off`) reach older records this way. It keeps the context and concurrency each suite ran with, lists the rescore in the manifest (`rescored`: when, SMA's commit, which suites), and rebuilds the summary and catalog. A LiveCodeBench attempt graded before SMA's patch (its `command.json` names no `patch`) has its saved code graded again first, with LiveCodeBench's own grader in the same image, at 6 seconds per test and 5 grading processes, with no network and no model (`patches/livecodebench/regrade.py`). The regraded file and `regrade.json` go to the attempt's `regrade/` folder beside the original grading, and `scores.json` names the regrade (`regrade`); `harness_metrics` stays the container's own first grading. A BrowseComp-Plus score whose questions met a server that was down (every retry failed, as runs before 2026-10-31 recorded them) becomes null, with the count and a pointer to `--redo browsecomp_plus`. A slot run's speed summary lists again the other runs on the serving machine during its speed step (`concurrent_load`), from the telemetry and engine counters they saved; before 2026-11-02 it missed every run that did not start or end a step during the speed step. It refuses a run with a step still running. Run records change only through SMA.

## Serving on another machine: the V100 slots

With `remote.enabled`, the model server runs on the lab's V100 pod and everything else stays on the Spark: the
clients, the grading, the records, `sma watch`. llama.cpp is the only engine there (Volta has no BF16, FP8, or
FP4), from a pinned source build; SMA downloads the GGUF files there from the run's pinned revision, checks
them against the Spark's hashes, starts `llama-server` over SSH, and forwards its port to `engine.port`. Runs
sit under `runs/<slug>/llamacpp-v100/`, and the manifest's `serving` names the hardware, the slot, the GPU,
and the build. A run resumed on another slot names that slot, and the slots before it stay in `serving.earlier`,
each with when the run left it; before 2026-11-02 such a run named only its first slot. KL compares only runs
served on the same hardware.

The pod's four GPUs are four slots (`remote.slots`), and `sma worker --slots` runs one leg of a queued job on
each, many at once (owner decisions 2026-11-01). Each leg takes the first free slot, in queue order; when one
ends, the next starts on that slot. A pair's three legs start together: the 4-bit legs' logprobs step waits
for the reference's logits (`logprobs.reference_wait_s`), and records KL as null with the reason if they do not
come. A failed leg resumes its own run on any free slot, up to `queue.max_attempts`. The speed steps of the
slots take turns, in arrival order, while the other slots keep working, and the speed summary records that
load (`speed_turn`, `concurrent_load`). LiveCodeBench's grading takes a machine-wide lock, so one container
grades at a time; the speed steps hold it too, since both are timed on the same fast CPUs. The dispatcher guards the harness's memory for all the slots and stops only the run using
the most; that leg resumes later, and a second stop fails it for good (`failed/<job>-leg<N>.json`). On the
harness GB10, SMA's containers run in their own systemd slice on fixed CPUs (`harness:`), apart from the
KernelBench service's. Details, the slot config, and the dispatcher's restart rules:
[`services/v100-serving/README.md`](services/v100-serving/README.md).

Run folders are committed to the repository. They are the data SMA submits and keeps. Git ignores only what cannot or must not go in:

- `logprobs/dump.json` (about 300 MB), `logprobs/kld-base.bin` (about 2.5 GB for a 0.6B model), and SWE-bench's `trajectories.jsonl.gz` are too big for git. They stay in the run folder on the machine that ran it. The manifest's `large_files` keeps each one's sha256 and size. `sma compare` and a llama.cpp KL reference check a copy against that hash and refuse one that does not match.
- BrowseComp-Plus's `trajectories.jsonl.gz` holds its questions and answers, which BrowseComp-Plus asks never appear as plain text online, so it stays out of git the same way. While a run is between its two BrowseComp-Plus steps, the per-question files under `quality/browsecomp_plus/queries/` hold them too; git ignores that folder, and the second step bundles it and removes it.
- `runs/catalog.sqlite` and `runs/index.json` are derived from the manifests. On a fresh clone, `sma list` rebuilds them.
- The repository root's `.env` holds this machine's settings and the lab machines' names (below). Git ignores it.

Before you commit run folders, run `sma publish-check --fix <run folders>`. It scrubs the run files again, as SMA scrubs what it writes, so a name added to the scrub list later (`V100_HOST`, 2026-11-02) reaches older files too. Then it refuses any file that still holds this machine's hostname, a token or something shaped like a key, a lab name from `.env`, or a name from `SMA_PUBLISH_DENY` (private repos, machines, projects; the list stays in `.env`). It names what it found, never the value, and an engine's own log can print anything, so a file SMA cannot rewrite safely (a binary) is only reported. It reads only what git tracks or would add (everything, with no path), so the files too big for git, whose sha256 the manifest keeps, are never read or rewritten. Documents are reported, not changed: a line that names the lab needs rewording. `.githooks/pre-push` runs the same check on every file a push would publish and refuses the push on a hit; turn it on once per clone with `git config core.hooksPath .githooks`.

Public files never describe the lab: no private repo or project names, no hypervisor, cluster, proxy, storage, or network design, and no server models. Benchmark conditions (GPU, clocks, CPU and memory limits, software versions) stay.

`runs/gb10/` and `runs/cpu/` hold baselines that are not SMA runs. They were measured on the lab's benchmark services, and each README says how to call its service during an eval:

- [`runs/gb10/baseline/kernelbench/`](runs/gb10/baseline/kernelbench/README.md): KernelBench levels 1–3 timed in eager PyTorch on a separate Spark's GB10 (fp32, `cuda_event`, 100 trials, clock locked at 2200 MHz). Compare speedups only within one environment fingerprint.
- [`runs/cpu/baseline/sweverified/`](runs/cpu/baseline/sweverified/README.md): SWE-bench Verified-mini's 50 tasks graded with their gold patches on the x86_64 runner (50 of 50 resolved). This shows every task image and test works there.

Machine names in those files are `${NAME}` placeholders. Their values are in the root `.env`, which git ignores: `set -a; . ./.env; set +a`.

Older runs that live at `runs/<model-slug>/<quant>/<run-id>/` are still found by `sma list`, `sma status`, `sma resume`, and `sma compare`. New runs are engine-separated. A resumed run keeps the engine and the thinking mode it was started with.

Schemas: [`schemas/manifest.schema.json`](schemas/manifest.schema.json) and [`schemas/summary.schema.json`](schemas/summary.schema.json).

JSON is written to a temp file, fsynced, and renamed. A crash does not leave a half-written manifest or summary.

The manifest is the subject record: model repo, revision SHA, weight hashes, quant, mixed composition when the config exposes layer or group counts, architecture check, parameter counts, engine name, image and digest, every server flag that was passed, the env vars SMA set, the MoE backend for quality and for speed, the SMA git commit, the host alias, timestamps, step status, and the sha256 and size of the files kept out of git. It does not contain the machine hostname or the HF token. `summary.json` uses null for anything that was not measured. It does not fill missing scores with zero. `quant` in the index is `mixed` for a mixed checkpoint.

Energy in `summary.json` is the sum over valid speed cells of the GPU's cumulative energy counter (NVML `nvmlDeviceGetTotalEnergyConsumption`), read just before and just after each bench command (`speed/windows.json` `energy_j`). That is how Zeus, AIPerf, and the ML.ENERGY benchmark measure energy. On a GB10 it updates more often than 4 times a second; under a steady 82 W load it read 3.4% below a 4 Hz power integral. When the counter cannot be read, that cell falls back to the 1 Hz `nvidia-smi` power integral, and `energy.method` says which was used (`mixed` when both). A gap longer than `telemetry.max_sample_gap_s` (default 2.5 s) is not bridged in the fallback. The 1 Hz sampler still records clocks, temperature, and throttle reasons for every cell.

## Config

`sma.yaml` in the working directory, or `--config`. Unknown keys are an error; `engine.max_model_len` and `engine.kv_cache_gib` say the memory plan replaced them. `--quantization` and `--tensor-parallel-size` other than 1 are refused, including inside `engine.extra_args`, and so are the KV type, context, and pool flags of all three engines (`--kv-cache-dtype`, `--max-model-len`, `-ctk`, `-c`, and the rest), which the memory plan sets. SGLang attention must stay `flashinfer` (required on SM12x). `--tp-size` is forced to 1.

The vLLM tag is pinned (`nvcr.io/nvidia/vllm:26.05.post1-py3`). The SGLang tag is pinned (`lmsysorg/sglang:v0.5.10.post1-cu130`, the versioned arm64 / CUDA 13 tag, not `latest-cu130`). The llama.cpp tag is pinned (`ghcr.io/ggml-org/llama.cpp:full-cuda13-b11913`, arm64 / CUDA 13 with SM 12.1 kernels; the "full" image has `llama-server` and `llama-perplexity`), and the run records llama.cpp's own build (`engine.build_info`). Set `engine.image_digest`, `engine.sglang_image_digest`, or `engine.llamacpp_image_digest` when you already know a digest. ### Memory on a Spark

The CPU, the GPU, the OS, and every process share one pool of unified memory, 130.7 GB on a GB10. An out-of-memory guard such as earlyoom stops `vllm` and `python` processes when free memory falls under its floor, and that looks like an engine crash. So SMA plans each run's memory before it starts anything, and refuses a run that cannot fit ([docs/serving-design.md](docs/serving-design.md)). SGLang is held to the plan in bytes as vLLM is (`--kv-cache-memory-bytes`): its `--mem-fraction-static` is the memory already in use plus the plan's weights and pool, over the total, and never above `engine.gpu_memory_utilization`; its pool is planned with sliding-window layers at full length, as SGLang allocates them. On 2026-10-30 a token-only cap let SGLang fill the Spark to its 0.9 share with LFM3-1.7B. As a last line of defense, a run's telemetry thread reads available memory every second, and if it falls under `memory.guard_free_gb` (12 GB) SMA kills that run's containers at once; the running step fails and the manifest says why. GPU memory on a GB10 is charged to no process, and earlyoom only sends SIGTERM, so neither stopped the 2026-10-28 run that took the whole Spark down.

- **Budget.** Weights, the KV pool, and the engine's own overhead stay under `memory.budget_gb` (100 GB). `memory.overhead_gb` holds the overhead per engine, measured on a Spark (see docs/first-spark-run.md): the engine's activations, CUDA graphs, and server processes, plus SMA's tools beside it (nel, the bench client). llama.cpp also sizes its compute buffers by its whole KV cache (the 16-bit attention mask for one 512-token micro-batch, on the GPU and again on the host, and one attention layer's K and V converted to 16 bits for flash attention: 6,144 bytes per token for Qwen3, 4,096 for LFM3), and keeps a prompt cache in host RAM (`engine.llamacpp_cache_ram_mib`, 8 GiB, llama.cpp's default, passed as `--cache-ram`). The plan counts both.
- **KV cache.** Always 8-bit: FP8 on vLLM and SGLang, Q8_0 on llama.cpp (34 bytes per 32 values). Never 16-bit. `engine.kv_cache_scales` records where the scales come from: the checkpoint, when it declares FP8 KV scales, or the engine's default of 1.0. It adds what the engine's log says it used: `nvidia/Qwen3-8B-NVFP4` declares FP8 KV scales, and all 72 are 1.0, so vLLM reports a scale of 1.0.
- **KV per token.** From `config.json` or the GGUF metadata: K and V values in the layers that attend to every token. Sliding-window layers count only their window. Linear-attention, convolution, and Mamba layers keep a small fixed state per stream instead (an estimate). Hybrid models such as Qwen3.6 or Nemotron-H need a fraction of a dense model's KV.
- **Context per stream.** 256K (`memory.start_context`), or the model's native maximum if smaller, then halves until one stream fits next to the weights. Native means without RoPE stretching. If a config ships with stretching on, the native maximum is its original length. SMA never turns stretching on.
- **KV pool.** Everything left in the budget. vLLM gets it as `--kv-cache-memory-bytes`, SGLang and llama.cpp as tokens. llama.cpp's pool holds its slots (`-np`) at the context per stream and no more, because no request can use more and its buffers grow with the whole cache. On 2026-10-28 a pool of the rest of the budget gave LFM3-1.7B 11.6 million tokens for 8 slots of 262,144, its buffers took 47 GB the plan did not count, and the Spark ran out of memory. `engine.gpu_memory_utilization` no longer sizes it; it is vLLM's startup free-memory check and SGLang's static share.
- **Per benchmark.** Each benchmark gets the largest step that fits the streams it runs at once: determinism 64, logprobs 1, quality `quality.concurrency`, speed the highest sweep concurrency. If even its least context (`memory.quality_min_context` for quality, the window for logprobs, the longest speed shape) does not fit, the run is refused before launch.

The plan is in `manifest.json` `memory_plan`. `summary.json` `deployment` says what someone gets running this model this way: the engine, the weight format, the KV type, the context per stream and why, and, computed before launch, the weight and pool sizes and the streams that fit at full context and at 32K. Measured during the run: the pool the engine reported, the streams it holds, the peak memory (`memory.csv`, the drop in available memory below the run's first sample), and output tok/s at 1, 4, and 8 streams. Its `sentence` states it in one line.

Quality runs NVIDIA NeMo Evaluator 0.3.0 (`nel eval run`) against the quality server's chat API (`/v1/chat/completions`). For each suite SMA writes `quality/<suite>/nel.yaml` and runs nel in that folder. Every request carries `seed` and `chat_template_kwargs` with `enable_thinking` for the run's thinking mode, which the quality server also takes as its default for suites that cannot send it (BFCL). A thinking-off run sends `temperature` 0 (`quality.temperature`); a thinking-on run sends none, so the engine applies the model's own sampling. Each request sends `max_tokens` 131,072 (`quality.max_tokens`, 128K, owner decision 2026-10-31), or none where the stream's context leaves less than that plus 4,096 for the prompt, so the answer may use the rest of it (`commands.answer_limit`). Before, no request sent one (owner decision 2026-10-29): normal answers from LFM3-1.7B stayed under 33K tokens in the suites and 49K in LiveCodeBench with thinking off, but answers that loop ran to the end of a 262K context, 2 hours or more each; 128K ends a loop in about half that and cuts nothing seen so far. The request timeout (`quality.request_timeout_s`, 4 hours) and the suite timeout (`timeouts.eval_s`, 24 hours) allow for the longest answers. With the old 4,096-token limit, LFM3-1.7B ran out of room on 30% of its MMLU-Pro answers, 60% of its GPQA answers, and a quarter of its MuSiQue answers with thinking off, and almost all of those scored wrong. Each suite's `scores.json` counts the answers that stopped at the limit (`answers_cut_off`, from nel's `model_traffic.jsonl`; null for BFCL). BFCL's container sends its own temperature (0.001) and no `max_tokens`, in both modes. nel's `reasoning` interceptor moves a leading `<think>` block out of the answer before it is scored. A chat template that does not read `enable_thinking` ignores it. Failed requests are retried `retries.attempts` times in all, each with `quality.request_timeout_s`. That limit reaches nel's model client too: nemo-evaluator 0.3.0 builds it with a fixed 120 s timeout that no config sets, so SMA runs nel's own console script under its own Python after raising that floor (`commands.NEL_CLIENT_TIMEOUT`); `command.json` records it as `client_timeout_s`. A `nel` that is not a Python script is refused. Before this, LFM3-1.7B's 4,096-token MuSiQue answers (about 123 s on a Spark) were dropped at 2 minutes and the suite's score was null.

A suite's `bench` is a nel benchmark: a built-in name (`mmlu_pro`, `gpqa`), `lm-eval://<task>` for a generative lm-eval task, or `sma:<name>` for a grader SMA ships in `src/sma/nel_benchmarks/`. SMA copies that file into the suite folder, so the grader that scored a run stays with it. `limit` picks that many questions by a seeded shuffle of the whole dataset (`shuffle_seed` = `seed`), so every model and quant answers the same questions. `scores.json` holds `pass@1`, its bootstrap interval, the question count, the failure count, and the dataset size. nel scores a request that never got an answer (a timeout or a server error: its `infra_error` and `graceful` failures) as wrong; SMA does not fill a missing score with zero, so a suite with any unanswered request has a null score and an `error` that says how many, and nel's number is kept as `pass_at_1_failures_as_wrong`. A reply nel categorizes as a refusal is an answer and stays in the score. The summary copies the score, the interval, and the count. `samples.jsonl` has one row per question (`problem_idx`, the response, the extracted answer, the reward); the full conversation stays in nel's `trajectories.jsonl`. nel writes its absolute output path into some files; SMA removes the hostname from every text file nel wrote, also when nel fails.

GSM8K uses `sma:gsm8k`: nel's own prompt and dataset with a numeric answer check. Both GSM8K graders in nemo-evaluator 0.3.0 mark answers wrongly. On a Spark run of Qwen3-0.6B (50 questions), the built-in grader read "The answer is: 140" as ": 140" and scored 0 of 50, and `numeric_match` strips trailing zeros (140 became 14, 2500 matched 25). SMA's check takes the first number after the last "answer is" or "answer:", or else the last number, and compares the values. It scored 27 of 50, the same as a hand count.

BFCL v3 (`bfcl_v3`, Berkeley Function Calling Leaderboard) runs NVIDIA's eval-factory container (`nvcr.io/nvidia/eval-factory/bfcl:26.03`, arm64 build) with task `bfclv3_ast`: single-turn, live, and multi-turn function calls, sent to the chat API with native tool calling, so the server's tool-call parser is part of what is scored. SMA runs the container itself, not through nel, because nel runs such containers in a temporary folder and deletes BFCL's per-question files. The image is pinned by the digest `docker image inspect` returns. The container runs with host networking (127.0.0.1 is the quality server), as the host user, and with `NEMO_EVALUATOR_TELEMETRY_LEVEL=0`; without that it reports the model name and task to NVIDIA. SMA runs 2,000 of its 4,441 questions (the suite's `limit`, owner decision 2026-10-31; all of them took about 6 hours a run, most of it the 800 multi-turn questions): an even share of every category, about 45% each, spread evenly through the category (`src/sma/patches/bfcl/sma_subset.py`). The container's own limit keeps the first questions after sorting by category name, which drops whole categories, so SMA patches it at run time like LiveCodeBench (mounted read-only on `PYTHONPATH`, only when the suite has a limit; `command.json` records the limit and each patch file's hash). The patch also makes BFCL's evaluator compare each answer with its own question and ground truth, which it pairs by position. `sma rescore` scores a run that answered all 4,441 on the same 2,000, so runs before and after the limit compare. The score is accuracy over every question, with a 95% Wilson interval; `samples.jsonl` has one row per question (`category`, `id`, `correct`). BFCL's own group scores (percent) are kept as `harness_metrics`; they are not the leaderboard's overall score. The quality server has prefix caching off, and BFCL repeats long tool lists every turn, so the multi-turn questions are slow.

A suite with `tools: true` needs the server's tool-call parser. It depends on the model (`hermes` for Qwen3, `llama3_json` for Llama 3, `qwen3_coder` for Qwen3-Coder on vLLM), so pass `--tool-parser NAME` to `sma run`, `run-pair`, `queue add`, or `queue add-pair`, or set `engine.tool_call_parser`. The manifest records it, and a resume keeps it. Without a parser, that suite records a null score with the reason, and the other suites run.

The `quality` extra installs `nemo-evaluator[lm-eval]` and `lm-eval[ifeval]` (`langdetect`, `immutabledict`, `nltk` for `lm-eval://ifeval`). lm-eval's log-likelihood tasks (multiple choice scored by probabilities, such as `global_mmlu`) cannot run over a chat API; nel refuses them.

## Caveats

- Batch invariance is beta, and SMA uses it only for unquantized checkpoints on vLLM. On a Spark (2026-10-27) it started with an FP8 KV cache on BF16 Qwen3-0.6B and the determinism probe passed. For quantized checkpoints vLLM's batch-invariant mode replaces the real kernels: it logged "VLLM_BATCH_INVARIANT forces NVFP4 linear to use the emulation backend" and served NVFP4 Qwen3-8B by dequantizing to BF16, at about 2 tokens per second per request, so its quality and KL numbers were not what an NVFP4 user gets. By owner decision (2026-10-27), NVFP4, MXFP4, mixed, and FP8 checkpoints run their real kernels with batch invariance off; `engine.batch_invariant_warning` says so, and the determinism probe records the batching noise that remains.
- Turning batch invariance on is not enough if async scheduling is still composing the next batch. vLLM quality mode also passes `--no-async-scheduling`. On a Spark (2026-10-27) vLLM 0.21 accepted it with batch invariance on.
- MoE backend auto-selection on SM121 can pick Marlin, and Marlin NVFP4 on SM121 has crash reports. vLLM MoE NVFP4 and MXFP4 set `--moe-backend` explicitly, then try `marlin` if `flashinfer_b12x` never becomes healthy. That is step 1 of the arena plan's NVFP4 chain. If every backend in the chain fails, the step is failed, not skipped. SMA does not quantize and does not switch to SGLang as a fallback.
- Some Spark units throttle or power off under a sustained load. Throttled speed cells are marked invalid. They are not deleted. `sw_power_cap` is recorded and, by default, does not invalidate the cell.
- Top-k KL on vLLM and SGLang is an approximation. The tail is one bucket. If a reference top-k id is missing from the candidate's stored top-k, that mass is folded into the tail and the position is labeled approximate. Positions that would have been infinite KL stay in the mean with probability floored at `1e-12`, and the count is `kl_floored_positions`. llama.cpp's KL is llama-perplexity's full-vocabulary KL over fewer tokens (8 chunks × 1,023 by default), and its perplexity scores the second half of each chunk. Neither is comparable with the vLLM numbers; `sma compare` refuses llama.cpp runs.
- The KV cache is 8-bit on every leg, so the BF16 leg is BF16 weights with an FP8 KV cache, not a 16-bit reference. KL between two legs measures the weights with the same KV type. A BF16 checkpoint has no calibrated KV scales; vLLM and SGLang use a scale of 1.0, which is what a production deploy with `--kv-cache-dtype fp8` gets too.
- The memory plan is computed. Engine overhead (`memory.overhead_gb`) was measured on a Spark with small models; a vision tower or a long-context activation peak can need more. The measured peak in `deployment.measured` is the check. vLLM pads hybrid models' KV pages, so its reported pool can differ from the plan.
- A config that ships RoPE stretching on gets its original length as the native context. gpt-oss ships YaRN with an original length of 4,096, so SMA plans it at 4,096 tokens. DeepSeek-style configs are the same.
- llama.cpp has no batch-invariant mode and caches prompts, so its quality and determinism numbers carry batching noise the vLLM quality server does not have. Its determinism probe failed on Qwen3-0.6B on a Spark, as expected.
- llama-server dropped one connection out of 32 at 8 concurrent streams in one speed cell on a Spark (`ServerDisconnectedError`). The cell was marked `bench_failed` and passed on its retry.
- A GGUF's sliding-window layers are counted as full attention when the file names no window pattern (gemma3, gpt-oss); the plan then overestimates their KV and fits fewer streams.
- Tokenizers must match. `sma compare` refuses otherwise. Tokens per answer are not a shared unit across models.
- NeMo Evaluator scores are not the arena's pinned scorers. The default suite list runs IFEval's 541 prompts, GSM8K 150 of 1,319, MMLU-Pro 700, GPQA Diamond's 198, MuSiQue 100, BFCL 2,000 of 4,441 (an even share of every category), and LiveCodeBench's newest 105 (owner decision 2026-10-29: 20 GPQA questions gave LFM3-1.7B's BF16 and Q4 intervals of 20-60% and 10-45%, too wide to separate two quants). The `gpqa_diamond` suite runs nel's built-in `gpqa`, whose dataset is gated on Hugging Face; accept the terms with the account whose token is in the environment or the Hugging Face token file. Clear `limit` to run a whole dataset. The arena's full suite set is not the default.
- KernelBench, SWE-bench, and BrowseComp-Plus run with the model's own sampling (owner decision 2026-10-27), not KernelBench's temperature 0, so a rerun can score a little differently and the numbers are not KernelBench's greedy leaderboard numbers. They send `enable_thinking` for the run's thinking mode (owner decision 2026-10-29; before, they used the template's default). A GGUF has no `generation_config.json`; llama-server applies the GGUF's `general.sampling` metadata if it has some (LFM3's: temperature 0.1, top-k 50, repeat penalty 1.1), and its own defaults otherwise. `settings.json` records the sampling and, beside the run's mode, the template's own thinking default (`thinking.template_default`). SMA renders the chat template as transformers does, with its `generation` tag (LFM3's template uses it). KernelBench's answers go up to 128K tokens (`kernelbench.max_tokens`, owner decision 2026-10-31), and never past the context per stream minus 4,096 for the prompt. BrowseComp-Plus keeps its client's 20,000-token budget per question.
- KernelBench's fast_1 counts a kernel faster than the baseline by any margin. The unchanged reference code scored fast_1 on the service (58.8 ms against 58.9 ms), so read fast_1 near 1.0× as noise.
- Each benchmark's recorded context is the plan's step for its streams. The server enforces only its own context, so an answer or an agent that runs longer than its step still runs, and the server may queue other requests behind it.
- Stopping a SWE-bench run ends its processes on the runner, but mini-swe-agent's task containers (`minisweagent-*`, `sleep 2h`, `--rm`) can stay up to two hours.
- BrowseComp-Plus scores are not comparable with its leaderboard. SMA asks 100 of the 830 questions, grades with Qwen 3.8 Flash on OpenRouter at temperature 0 (since 2026-11-04; the lab's FP4 copy of it from 2026-11-01 and Ornith 1.5 122B before, so runs judged by each are not compared) instead of Qwen3-32B at 0.7, and runs every model through the repo's native-tool chat client, while the published small-model rows used other clients (Qwen-Agent's text tool calls for Qwen3-32B, the Responses API for gpt-oss). For orientation, the leaderboard's BM25 accuracy: Qwen3-32B 3.6%, gpt-oss-20b at high effort 21.5%, Tongyi-DeepResearch-30B-A3B 34.0%. General models score near zero, and over 100 questions a score's 95% interval is about ±9 points at 30%.
- The judge checks ([`docs/judge.md`](docs/judge.md)) used answers from GPT-5 and o3, which follow BrowseComp-Plus's answer format; neither judge has been checked on small models' answers. A judge reply without a verdict counts as wrong, as in BrowseComp-Plus; the run warns with the count.
- MuSiQue has no published score for small chat models in SMA's setting (all paragraphs in the prompt, zero-shot, greedy, thinking off). Published numbers use other prompts, subsets, or retrieval, and vary widely; compare MuSiQue scores only between SMA runs.
- Speed repeats default to 1, plus a warm-up. The arena plan's "at least 3 runs" is `speed.repeats`.
- Energy is GPU only (`scope: gpu`): the NVML counter per valid speed window, with the 1 Hz power integral as a fallback. On a DGX Spark the CPU shares the 140 W SoC budget and is not counted, and there is no on-box system-power counter. It is not joules per correct answer and not a wall-meter reading.
- The bandwidth ceiling in the summary uses the configured 273 GB/s spec constant and approximate bytes per parameter. It is not a measurement. NVFP4 scale overhead is not included. Mixed checkpoints have no single byte width, so that ceiling is null.
- The determinism probe sends one completions request with N copies of each prompt, with prefix caching disabled on the quality server. The client cannot force the scheduler to fuse those copies into one batch. `max_num_seqs` is at least 64 so a batch of 64 is allowed.
- Logprobs go through the server that is already up. A second offline `LLM()` process is not started, because the quality server already holds the GPU.
- SGLang measurements that the bench JSON or `/metrics` scrape does not contain are null, with a reason on the cell or in `metrics.json`. They are not copied from vLLM's metric names.
- SMA does not apply arena fidelity verdicts (broken / degraded / faithful / lossless). It records KL, top-1, and perplexity. Thresholds belong to the arena.

Found on the Spark and fixed in SMA:

- vLLM 0.21 rejects `--linear-backend` ("unrecognized arguments"), so every dense NVFP4 run failed to start. SMA now sets `VLLM_NVFP4_GEMM_BACKEND`.
- vLLM's batch-invariant quality mode served NVFP4 by emulation, at about 2 tokens per second per request for an 8B model, so no NVFP4 quality or KL number measured the real kernels. Quantized checkpoints now run with batch invariance off (owner decision).
- A suite whose requests timed out was scored as if they were wrong answers (GSM8K read 0.2 with 8 of 10 requests unanswered). A suite with unanswered requests now has a null score and says how many; a refusal still counts as an answer.
- NVIDIA's Qwen3-8B NVFP4 checkpoint declares FP8 KV scales that are all 1.0; the record said "checkpoint" scales. It now adds what the engine's log says it used.
- SGLang's deterministic mode crashed at CUDA-graph capture ("DeepGEMM ... Unsupported architecture"), with a 16-bit or an FP8 KV cache. SMA sets `SGLANG_ENABLE_JIT_DEEPGEMM=0`.
- SGLang's architecture registry query ran without a GPU, so SGLang's registry dropped Qwen3 and preflight refused it. The query now runs with `--gpus`.
- SMA's own logprob step built the whole per-token dump in memory, 7 GB beside the KV pool, and one run peaked at 107.4 GB. The dump is now streamed to disk one window at a time.
- llama.cpp's compute buffer is sized by its whole context (about 12% of the KV pool), and its prompt cache can take 8 GiB of host RAM. A run peaked at 110.6 GB until the plan counted both.
- The default Hugging Face cache path is under the home directory, which holds the hostname on a machine whose user name is its hostname; fetch refuses it, as designed. Set `hf.cache_dir` outside your home directory.

## Benchmark services

KernelBench, SWE-bench Verified-mini, and BrowseComp-Plus's search run on other machines: a second GPU machine compiles and times the kernels, an x86_64 Docker host runs the agent's tasks, and an x86_64 machine (it can be the same one) holds BrowseComp-Plus's index and answers its searches. [`services/`](services/README.md) has all three, with how to deploy your own copy and how to call it. The judge that grades BrowseComp-Plus is described in [`docs/judge.md`](docs/judge.md).
